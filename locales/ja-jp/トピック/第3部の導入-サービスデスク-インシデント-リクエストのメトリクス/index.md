# 第3部の導入：サービスデスク、インシデント、リクエストのメトリクス

**サービスデスク、インシデント、リクエストのメトリクスは、サポートと復旧が、サービスを使う人々にとってどれだけうまく機能しているかを示します。それによって、レポートの見栄えではなく、助けを得る体験を改善できます。**

この部は、ユーザーがサービスと出会う場所を扱います。サインインできない人、注文が失敗した顧客、新しいノートパソコンが必要な従業員は、みなサービスデスク、監視のアラート、セルフサービスのポータル、チャットのメッセージを通じて組織に届きます。その次に起きることが、サービス全体をどう判断するかを決めます。この領域のメトリクスは、その体験を二つの側から記述します。何かが壊れたときに、組織がどれだけ速く、どれだけうまくサービスを復旧するか、そして、人々が出す定型のリクエストを、どれだけ確実に履行するかです。

ITIL 4 では、インシデント管理とサービスリクエスト管理は別のプラクティスであり、サービスデスクは両方の窓口です。自分たちが作ったものを運用するアジャイルのチームは、同じ仕事を、オンコールのローテーションと共有のキューで扱うことがよくあります。どちらの場合も、測定の問題は似ています。件数は仕事がどう分類されるかに依存し、時間は時計がどこで始まり止まるかに依存し、平均はユーザーが覚えている長い遅れを隠します。第1部で述べた統計の習慣は、全体に当てはまります（トピック1.6「サービスメトリクスのための統計リテラシー」を参照）。

サポートのメトリクスは、異例なほどゲーミングされやすいものでもあります。デスクは、チケットを早く閉じることで、より速く閉じられ、通話者を急かすことで、対応時間を下げられます。チームは、インシデントをリクエストに再分類することで、インシデントの件数を減らせます。そのため、この部の各トピックは、メトリクスが報いる振る舞い、それが隠す振る舞い、その違いを捉える防護柵に名前を付けます（トピック1.2「グッドハートの法則とメトリクスの心理学」を参照）。ここにあるすべての測定値は、チーム、サービス、またはシステムを記述します。どれも個々のエージェントや対応者の順位付けはしません。

## この部のトピック

- **3.1 サービスデスクのメトリクス**：問い合わせ件数、初回問い合わせでの解決、放棄、対応時間。それぞれが何に報い、何を隠すか。
- **3.2 インシデントの件数と優先度**：インシデントの件数、カテゴリ、影響と緊急度、優先度の構成、繰り返されるインシデント、利用量に対する件数の正規化。
- **3.3 インシデントの対応時間と解決時間**：検知、確認、対応、解決までの時間。平均時間の測定値とその統計上の問題。代わりにパーセンタイルを使います。
- **3.4 重大インシデントのメトリクス**：頻度、継続時間、顧客への影響、コミュニケーションの適時性、アクションのやり遂げ。
- **3.5 サービスリクエスト履行のメトリクス**：履行時間、バックログ、カタログ項目ごとのリクエスト件数、自動化の割合。
- **3.6 ナレッジマネジメントのメトリクス**：記事の利用、解決での再利用、リンク率、鮮度、Knowledge-Centered Service（KCS）の指標。
- **3.7 セルフサービスと自動化のメトリクス**：デフレクション、セルフサービスの成功、自動化のカバー率、件数と複雑さに対するシフトレフトの効果。

## これらのトピックの相互関係

最初の四つのトピックは、障害の生涯をたどります。問い合わせはデスクに届き、それがトピック3.1の関心事です（トピック3.1「サービスデスクのメトリクス」を参照）。不具合を報告するものはインシデントになり、トピック3.2（トピック3.2「インシデントの件数と優先度」を参照）が、それを数えて、影響と緊急度で分類します。次に、トピック3.3（トピック3.3「インシデントの対応時間と解決時間」を参照）が、各ステージにどれだけ時間がかかるかを測ります。深刻な被害を引き起こす少数のインシデントは、その稀少さと大きさが通常の平均を誤解させるので、トピック3.4（トピック3.4「重大インシデントのメトリクス」を参照）で独自に扱われます。

これらの測定値の多くは、誠実さを保つために、相棒を必要とします。トピック3.1の対応時間のような、デスクでの速さは、初回問い合わせでの解決と、それが生む再問い合わせと並べて読むべきで、速い通話が解決された問題と取り違えられないようにします。トピック3.3の解決時間は、トピック3.2の繰り返されるインシデントとともに見るべきです。一週間後にまた失敗する素早い復旧は、ユーザーの役に立っていないからです。トピック3.2の優先度の構成は、あらゆる時間の測定値に文脈を与えます。解決時間の中央値の上昇は、チームの対応がどれだけうまいかの変化ではなく、到着するインシデントの種類の変化を反映しているかもしれません。

リクエストとインシデントは並べて測るべきですが、決して統合してはいけません。トピック3.5（トピック3.5「サービスリクエスト履行のメトリクス」を参照）は、予測可能で繰り返せる履行の仕事を扱い、そこでの目的は、リクエストごとの安定した、縮小していく労力です。インシデントの仕事は予測不可能で、その目的は、速く持続する復旧です。両者を一つのキューの平均にまとめると、両方の問題が隠れます。第2部のフロー指標は、共有の時計と、二つの流れが互いを飢えさせないようにする仕掛かり作業の制限を提供します（トピック2.9「運用作業と計画外作業」を参照）。

最後の二つのトピックは、他のトピックが測る件数に働きかけます。トピック3.6のナレッジ（トピック3.6「ナレッジマネジメントのメトリクス」を参照）は、前の人が学んだことを次の人が再利用できるようにすることで解決を短縮し、トピック3.7で測られるセルフサービスのコンテンツに情報を提供します（トピック3.7「セルフサービスと自動化のメトリクス」を参照）。デフレクションと自動化は、デスクに届く単純な問い合わせを減らし、残った人々には、より難しい仕事の構成が残ります。この変化は予期されるべきで、結果として対応時間が上がることもあり、それはパフォーマンスの低下ではなく、構成の変化として読むべきです。

繰り返されるインシデントは、第4部の問題管理への入力になります。
